# 商业化 SaaS 管理中台 · 思路与缺口分析

> 目的：把当前这款**桌面版 AIGC 视频生成辅助工具**，评估升级成可对外收费的 **SaaS + 统一管理中台**还缺什么。
> 本文只谈**架构思路、缺口清单、决策项、路线图**，不含代码。

---

## 0. 一句话结论

你的**客户端商用钩子已经写了大半**（卡密激活 / 机器码绑定 / 令牌缓存 / 定时复核 / 每请求四件套鉴权头 / 网关线路接口），本地甚至已有 `org_members`、`org_line_owners`、`local_ad_accounts(secret_enc)`、`local_licenses/customers` 这些"半个中台"的表。
**真正缺的是服务端**：把这些客户端已经在调用的契约真正实现出来，再补齐**计费计量、中央数据库与多租户、API 网关本体、媒资存储、运维与合规**。
所以方向不是"重做客户端"，而是"**建后端 + 建中台前端 + 补商业闭环**"。

## 1. 现状盘点（你已经有的资产）

| 能力 | 现状 | 位置 |
|---|---|---|

| 组织 / 角色 / 部门 | ⚠️ 本地表已存在，无服务端 | `org_members(pass_hash,role,dept,active,last_login)`、`org_depts` |
| 线路归属 | ⚠️ 本地表 | `org_line_owners(account→owner)` |

**推论**：客户端已经把"要跟一个中台对话"的接口都定义好了。服务端只要**照这套契约实现**即可对接，改造成本低、风险可控。

## 2. 目标形态（中台要长成的样子）

- **交付形态**：桌面客户端（现有）+ 云端 SaaS 后端 + Web 管理台（给运营/客户管理员）。
- **角色**：平台运营方（你）、企业租户管理员、普通使用者、财务。
- **核心闭环**：登录鉴权 → 授权/额度校验 → 网关代理上游多模态线路 → 计量计费 → 产物存储分发 → 审计运维。
- **租户模型**：一个企业 = 一个租户（tenant），成员/部门/线路/任务/账单都挂在租户下，强隔离。

## 3. 客户端 ↔ 服务端「已有契约」（服务端必须照此实现，别推翻）

| 客户端调用 | 语义 | 服务端要提供 |
|---|---|---|
| `POST /auth/activate {card_key, machine_code}` → `{card_key, token, expire_at}` | 卡密换令牌并绑定机器 | 卡密池、机器绑定表、签发短期 token、一卡多机限制 |
| `POST /auth/verify {machine_code, token}` → `ok/expired/offline…` | 续用复核（24h） | 令牌校验、到期判定、机器码一致性、吊销名单 |
| 每请求头 `X-License / X-Machine / X-Ts / X-Nonce` | 网关鉴权 + 防重放 | 校验 token、机器码匹配、时间戳窗口、nonce 去重表（Redis） |
| `GET /lines`（带四件套） | 拉取当前可用生成线路 | 线路注册表（真实上游 base/key **只存服务端**）、按租户配额下发 |
| 业务调用经 `api_client` 转发到线路 `base` | 提交/轮询生成任务 | 网关做**反代**：客户端永不持有上游 key |

> 关键约束：**上游真实密钥（GPU/多模态服务）绝不能进客户端/exe**。客户端只拿到 `token`，真实 key 由网关在服务端注入。这是商用化的安全底线。

## 4. 缺口分析（按维度：现状 → 缺口 → 要做）

### 4.1 身份认证（AuthN）
- 现状：本地 `pass_hash`、卡密+机器码。
- 缺口：无集中登录、无会话/令牌体系、无找回、无 2FA、无登录审计。
- 要做：账号体系（邮箱/手机号+SSO 可选）、JWT/短期令牌 + refresh、密码策略与找回、可选 MFA、登录日志与异常检测、桌面端与 Web 端统一身份。

### 4.2 授权与多租户（AuthZ & Tenancy）
- 现状：`role/dept` 在本地、无租户概念。
- 缺口：**没有 tenant_id 贯穿数据**；行级权限、跨租户防越权完全缺失。
- 要做：租户模型（tenant/组织/部门/成员）、RBAC（平台角色 + 租户内角色）→ 演进到 ABAC、**所有表/查询/存储路径都带 tenant 前缀**、网关按 token 解析 tenant 并强制隔离、审计"谁在哪个租户做了什么"。

### 4.3 API 网关（本体尚不存在）
- 现状：客户端已按"有网关"来写。
- 缺口：**网关服务端还没建**。
- 要做：统一入口与路由（`/auth`、`/lines`、生成任务反代到上游多模态线路）、鉴权校验、**限流/配额/QPS**、nonce 防重放、熔断与重试、灰度/版本、请求与用量日志、密钥在服务端注入。

### 4.4 线路与密钥治理
- 现状：线路 base 写配置或走 `/lines`；`secret_enc` 已有字段。
- 缺口：真实上游 key 未托管、无轮换、无按线路成本计量。
- 要做：线路注册中心（上游 base/key/concurrency/健康探测——复用你已有的"状态灯基于真实检测"逻辑）、密钥 KMS 托管 + 定期轮换、BYOK（允许企业自带上游 key）作为可选商业模式。

### 4.5 计费与订阅（几乎全缺 · 商业闭环核心）
- 现状：无。
- 缺口：没有计量、套餐、额度、支付、账单、欠费控制。
- 要做：
  - **计量口径**：按任务数 / 按生成秒数 / 按 token / 按成品视频条数（你 `runs` 已有 `gen_sec/queued_sec/duration`，天然可做按秒计量）；上游 GPU 成本 vs 售价的毛利模型。
  - 套餐/订阅（月/年）、预充值钱包/点数包、后付费、超额熔断或降级。
  - 支付：国内微信/支付宝、海外 Stripe；发票与税务（对接开票）。
  - 账单、用量报表（复用 `range_stats` 的日/时聚合思路搬到服务端）、欠费提醒。

### 4.6 数据层：本地 SQLite → 云端库
- 现状：单机 `data/aigc.db`（SQLite），160 任务/206 执行都在本地。
- 缺口：无中央库、无多端同步、无并发写、无 schema 迁移治理。
- 要做：PostgreSQL（多租户）、schema 版本化与迁移（Alembic 类工具）、**离线优先双向同步策略**（桌面工具常离线：把现在依赖"NAS 租约/负载均衡"的调度逻辑重定位到服务端队列 + 客户端 outbox 增量同步，冲突以服务端为准）、备份/恢复/容灾、冷热分离（历史任务归档）。

### 4.7 媒资与产物存储
- 现状：成品视频落本地 `outputs/` 或 NAS，文件名带业务语义。
- 缺口：SaaS 需要可扩展的对象存储 + 分发。
- 要做：对象存储（OSS/S3 兼容）+ CDN、按租户隔离的桶/前缀、生命周期与回收站（你已有 `output_trash`/归档思路）、带宽与存储成本计量、下载鉴权（短期签名 URL）。

### 4.8 安全
- 现状：`secret_enc`、机器码、nonce 防重放雏形。
- 缺口：加密主钥管理、传输/静态加密、桌面端逆向防护。
- 要做：全链路 TLS、静态加密与密钥分级（KMS，`secret_enc` 的主钥绝不能打进 exe）、nonce/ts 服务端化、依赖与镜像扫描、最小权限、**诚实预期：桌面客户端鉴权天然可被破解**，把"值钱的东西"（上游 key/真实算力/数据）全部留在服务端，客户端只做薄壳——这是桌面转 SaaS 的根本安全策略。

### 4.9 合规与隐私
- 现状：`risk_rules` 内容风控雏形、发布记录。
- 缺口：生成内容合规标识、数据隐私、留存与资质。
- 要做：
  - **生成式 AI 合规**（中国）：算法/模型备案、内容审核、**AI 生成显著标识/水印**（你已有审片/标记机制可扩展）、日志留存。
  - 个人信息保护：个保法/GDPR、数据出境评估（若用海外上游多模态线路尤其关键）、用户协议与隐私政策。
  - 平台资质：涉及广告/发布（你有 `publishes`、广告主 `local_ad_accounts`）→ 相关投放资质。
  - 财税：电子发票、跨境结算。

### 4.10 可观测性与运维
- 现状：本地 `logs/`。
- 缺口：无集中日志/指标/告警/链路、无弹性伸缩。
- 要做：结构化集中日志、指标（P0：任务成功率、时延、线路健康、单位成本）、告警、分布式追踪、**GPU 侧弹性伸缩与队列削峰**（`runs` 的排队/生成用时数据正好用来建模容量）、部署（容器/K8s）、多环境（dev/staging/prod）、灰度发布。

### 4.11 分发与升级（桌面端）
- 现状：PyInstaller 打包、首次运行向导、配置包分发。
- 缺口：无自动更新与版本治理。
- 要做：**客户端自动更新**（签名校验、增量更新）、服务端↔客户端**版本兼容矩阵**（协议演进不能强更）、配置/线路包下发、崩溃上报。

### 4.12 管理后台（中台前端，你正要的那个）
- 现状：桌面里有"接口管理/设置"等页，但是**单机的**。
- 缺口：没有面向运营/租户管理员的 **Web 中台**。
- 要做：租户与成员管理、线路与密钥管理、执照/客户/卡密管理、订单与账单、实时用量与成本报表、审计日志、工单/公告、内容风控规则维护、开关与灰度配置。

### 4.13 商业与运营（非技术但决定生死）
- 定价与试用策略（免费额度/限时试用/席位价/按量价）、目标客户画像（KOL 带货/MCN 素材量产？）、SLA、客服与实施、文档与上手引导（你已有 pages_guide 可搬成帮助中心）。

        │               │               │
   [认证服务]       [计费/计量服务]   [线路注册/调度]
   (authN/租户)     (套餐·钱包·账单)  (反代上游多模态·健康探测·BYOK)

## 6. 分阶段路线图

- **阶段 0 · 地基（先别写业务，先把契约落地）**
  服务端实现 `/auth/activate`、`/auth/verify`、`/lines` + 网关鉴权（校验四件套、nonce 去重）+ 上游 key 托管；把 SQLite 迁到带 `tenant_id` 的 PostgreSQL。
  验收：现有桌面客户端不改 UI，仅填 `GATEWAY_BASE` 就能激活、拉到线路、经网关跑通任务。

- **阶段 1 · 最小可收费（MVP SaaS）**
  账号/租户 + 卡密→订阅/套餐 + 基础计量（按秒/按成品）+ 一个后台管理台雏形（用户/线路/用量）。
  验收：能开户、能收一笔钱、能限制额度、能出账单一页。

- **阶段 2 · 商业闭环 + 规模化**
  钱包/预充值 + 支付/发票 + 欠费熔断 + 对象存储/CDN + GPU 弹性伸缩 + 多端离线同步 + 可观测/告警。
  验收：并发上来不崩、成本可核算、毛利为正、断线可用。

- **阶段 3 · 合规与产品化**
  生成内容标识/审核、等保/备案、隐私与数据出境、SLA、帮助中心、灰度与 A/B。
  验收：过合规审查、可对大客户签 SLA。

## 7. 需要你先拍板的关键决策（Open Questions）

1. **交付形态**：纯"桌面客户端 + 云后端"就够，还是要加 Web 端做重协作？（影响多端鉴权与数据同步复杂度）
2. **部署边界**：公有 SaaS（多租户强隔离，运营重）还是也支持私有化部署（大客户）？还是先只做单机授权版？
3. **算力归属**：✅ **已定** —— 运营方（你）托管线路与上游密钥、把一切预先配好、**客户拿卡即用**；BYOK 暂不做。详见 §10。（此选择使计量/额度/熔断/防破解从"可选"变为"上线即必须"。）
4. **计费单位**：按席位/按任务/按生成秒/按成品条数/按点数？（`runs.gen_sec/duration` 支持按秒，`tasks` 支持按成品）
5. **桌面端防破解容忍度**：接受"薄客户端 + 值钱东西全在服务端"的现实，还是投入做更强 DRM（ROI 通常低）？
6. **目标规模**：先服务多少租户/日活/并发任务？决定要不要一上来就 K8s/GPU 池。

## 8. 现实提醒（少踩坑）

- **最大杠杆**：把上游真实密钥/算力/数据**全部收到服务端网关之后**，客户端只做薄壳——一举化解"exe 里藏 key 被逆向"这个桌面商用最大风险。
- **你选了"托管 + 卡密即用"，就承接了上游成本与容量风险**：BYOK 虽能砍掉一半复杂度，但已被否（客户体验优先）。对策是**走预付费点数包**把现金流风险前置给客户，并用**托管云服务**把单人运维压到最低（见 §10）。
- **别推翻已有契约**：客户端四件套、`/auth/*`、`/lines` 已定，服务端照实现即可，省一轮联调。
- **离线工具转 SaaS 的隐性成本在"同步"**：桌面经常离线，任务状态/产物归属的双向同步与冲突解决要提前设计，别等数据打架了再补。
- **合规对生成式内容越来越硬**：内容标识、审核、备案、隐私，越晚补越贵。

## 10. 已定商业模式：卡密预配 · 开箱即用

> 决策：§7-3 定为「运营方（你）托管线路与上游密钥，把一切预先配好，客户拿卡即用」，BYOK 暂不做。本节说明它如何改写其它章节的重点。

### 10.1 这个选择意味着什么
- **客户端几乎不用改**：现有 `输卡密 → /auth/activate → 拿 token → GET /lines → 跑任务` 就是"拿卡即用"的完整闭环；卡密成为**发放单元**。
- **计量/额度/熔断从"阶段 2"提前到"上线第一天"**：算力与密钥都在你手里，**每跑一次都在烧你的钱**，所以到量熔断是硬需求，不能等。
- **防破解/防滥用是生命线**：卡密被盗或被共享＝直接亏损。机器码绑定（已有）+ 一卡多机上限 + nonce 防重放 + 异常用量告警 + 远程吊销。
- **密钥纪律**：真实上游 key 只在网关之后（复用 §3/§5），`/lines` 下发的是**网关代理地址**，绝不是真实 base+key。

### 10.2 卡密 = 一个预配好的套餐（一张卡打包的内容）

| 维度 | 说明 |
|---|---|
| 线路包 | 这张卡能用哪些线路/模型（`/lines` 按卡返回子集） |
| 额度 | 预充值点数 / 成品条数 / 生成秒数（对应 §4.5，先定一种口径） |
| 有效期 | 到期日 `expire_at`（客户端已处理 expired 态） |
| 并发/机器数 | 同时几台机器、几条并发（对应线路 concurrency） |
| 租户归属 | 发卡给哪个客户/渠道（把 `local_customers/licenses` 概念搬到服务端） |

### 10.3 发卡 → 核销 → 续费 闭环（中台管理台要做的核心）
1. **生成卡密**：选套餐模板（线路包+额度+有效期+机器数）→ 落库（卡密池，状态"未用"）。
2. **分发**：渠道或你手动发给客户。
3. **首次激活＝拿卡即用**：客户在桌面输卡密 → `POST /auth/activate` → 校验未用 + 绑机器码 → 签发 token + 回写额度/到期 → 状态"已激活"，零配置。
4. **使用期**：每请求四件套 → 网关鉴权 + 扣减额度 + 到量熔断；`/auth/verify` 每 24h 复核。
5. **续费**：同卡追加额度/延期，或换新卡继承机器绑定。
6. **风控**：吊销、异常检测（短时间多机器/超量）、退款黑名单。

### 10.4 这条路的代价与单人团队的现实对策（诚实）
- **你承担上游成本与容量规划**，现金流先垫 → 用**预付费点数包**（先充值后消耗）把风险前置给客户，**别做后付费**。
- **单人运维很重**（网关+库+监控+客服都你一人）→ 强烈建议**用托管服务把运维降到最低**：云托管 PostgreSQL、托管 Redis、容器/Serverless 平台，**冷启动别自建 K8s、别自建 GPU 池**（先转售已有 SaaS 上游 API）。
- **计费口径推荐"点数"**：最通用，把上游各线路成本换算成点数倍率即可，客户易理解、你易调价。

### 10.7 计量与账务：点数 + 双层账
- **点数＝唯一对外计价单位**；两条计量源分别折算点数：① 脚本拆解按 token/次；② AIGC 生产按生成秒/时长。
- **双层账并行**（你特别强调的点）：
  - **下游账**＝客户点数消耗（收入侧，控额度/熔断客户）。
  - **上游账**＝你垫资线路的真实成本（成本侧，盯毛利）。核心 AIGC 按时间付费、豆包按量计费，两类成本分开跟踪。
  - **毛利＝点数售价 − 上游成本**；每线路/模型维一张"上游成本→点数"倍率表。
- **上游成本监控 + 消费预警防熔断**：你垫付算力，一旦被供应商账户额度/余额打满会中途熔断，砸所有客户。做法：抓各上游（豆包/火山、按时长的 GPU 等）的余额与消费，接其额度/账单 API 或控制台阈值，设多级预警（如 80%/90%/95%），逼近就告警/降速/切线路/暂停发卡，**别等被砍**。

### 10.8 用量校验：云端为唯一真源 + 脱机不可用
- 本地点数缓存**只是显示镜像，不作裁决**；权威余额/用量在服务端账本。
- 每次经网关的请求：服务端扣减并回传剩余，客户端回显向服务端对齐。
- 本地怎么改缓存（改 `license.json`/SQLite）都无效：提交时服务端重算、**以云端为准**，对不上就拒绝/纠正。
- **脱机即不可用**：因为线路经网关反代、脚本拆解/翻译也走网关，断网＝够不到网关＝跑不了任何计费动作；据此**去掉现有 `license.py` 的离线宽限**（现在缓存可撑到下次 24h 复核），改成"核心功能强在线"。
- **双向校验**：客户端上报本地用量 → 服务端权威值回传覆盖 → 差异记录进审计（识别篡改/异常）。

### 10.9 坐席生效：机器码绑定（否则坐席形同虚设）
- 一张卡＝ N 个坐席＝最多 N 台机器。激活时 `machine_code` 绑定并计入；每请求带 `X-Machine` 校验；超出坐席数拒绝；支持受控换绑（解绑旧机需限频/审批，防轮换共享）。
- 现有 `machine_code`（Win GUID + uuid node，不含用户名）已具备；补服务端"卡↔机器集合"表与坐席计数、换绑策略。
