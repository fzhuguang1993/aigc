# 本地文件搜索（唤出面板 · Everything 式）

全局快捷键唤出的搜索面板里，除了原有的**工具**结果，还多了两段本地结果：
**📁 文件**（按文件名/所在目录，全盘）与 **📄 文档内容**（按正文全文检索，文档目录）。
三条索引腿在**软件启动时**就于后台线程跑起来，不等用户第一次敲字。

代码分三层：

```
core/fileindex.py        索引本体：建库 / 全盘增量扫描 / bigram 全文索引 / 抽取 / 搜索
                         （纯 stdlib + pypdf/openpyxl，不 import 任何 Qt，能脱离界面单测）
workers/file_watcher.py  后台线程：启动延迟 3 秒 → 扫文件名 → 抽正文 → 每 120 秒一轮
gui/dialogs_launcher.py  三段结果展示 + 键盘导航 + 打开/打开所在目录/复制
gui/pages_settings.py    「🔍 本地文件搜索」设置卡（开关、范围、上限、立即重建、状态行）
```

---

## 🎯 怎么用

面板里直接打字即可，三段结果同一条导航链（工具卡在上、「📁 文件」居中、「📄 文档内容」在下，
文件段最多 30 行、文档段最多 12 行）：

| 操作 | 工具结果 | 文件结果 | 文档内容结果 |
|------|---------|---------|-------------|
| `Enter` / `Tab` | 唤出该工具 | 打开文件 | 打开文档 |
| `Ctrl+Enter` | 等同 `Enter` | 📁 打开所在目录 | 📁 打开所在目录 |
| 右键 | — | 🚀 打开 / 📁 打开所在目录 / 📋 复制路径 / 📎 复制文件 | 同左 |
| `↑` `↓` | 按**行**上下跳（工具卡是一排多个，所以这才是跨行） | | |
| `←` `→` | 按**列**左右跳；文件与文档都是一行一条，于是等同 `↑↓` | | |
| `Esc` | 收起面板 | | |

四个方向键都在搜索框那一层被面板接管（`eventFilter`）：`QLineEdit` 会把 ←→ 当自己的光标键
接住、事件根本不往下传，不接管就是"上下灵、左右不灵"。**代价写在明面上：搜索框里不能用
←→ 挪编辑光标了**——打字时游标本来就在末尾，改错了用 Backspace/Home/End 或鼠标。

- 「复制文件」写进剪贴板的是 CF_HDROP（粘出去是文件本体，能直接拖进微信/资源管理器）；
  「复制路径」是纯文本路径。两者共用 `utils/desktop_utils`，不另写一份。
- 索引还没建好时**不报错**：文件段位置显示一行灰字「本地文件索引建立中：已收录 N 个文件」，
  已入库的部分照常命中。
- 输入停止 120 毫秒才发一次查询；每次查询带一个自增 `seq`，后台回来的结果 `seq` 不是最新的
  就直接丢弃——否则慢查询会盖在快查询上面，出现"打的字和结果不对应"。

设置页那张卡的默认口径：**开 / 全盘 / 搜正文开 / 单文件 20MB**。改任一开关都会立刻落盘并催
后台线程（`file_watcher.kick()` 把下一轮提前，不用等那 120 秒）。

## 🧮 实测数字（本机一次完整跑出来的原始结果）

```
索引范围   C:\ D:\ E:\ F:\ G:\（只认固定盘 DRIVE_FIXED）
首扫       949,023 个文件 / 122,989 个目录 / 45.3 秒
增量二轮   added=1，其余不动 / 14.8 秒（全盘照走，只差分签名变了的目录）
抽正文     indexed=1,496 篇 / skipped=72,225 个（扩展名不在名单里）/ 55.2 秒
索引库     729.3 MB
中文两字词「关节 / 骨胶原 / 钩子 / 拆解」在真实 PDF、docx、txt、md 上全部命中并带 snippet
```

热缓存下单独跑一趟排除后的目录树是 95.1 万文件 / **7.8 秒**；上表 45.3 秒是"五个盘 + 边扫边落库
+ 逐目录提交"的真实开销。冷盘（刚开机、文件系统缓存空）预期 30–90 秒，所以首扫压在启动后的
后台线程里，绝不压在第一次敲字上。

## 📏 索引范围与排除清单

**文件名索引＝全盘**，但命中下面这些目录名就剪掉**整棵子树**（大小写不敏感）：

```
$RECYCLE.BIN  System Volume Information  Windows  WinSxS  ProgramData  AppData
assembly      Temp                       Installer  SoftwareDistribution  Recovery
PerfLogs      node_modules               .git       .venv / venv          __pycache__
$WINDOWS.~BT  Config.Msi                 windows.old  microsoft           searchplugins
code store
```

这条清单不是洁癖，是 10 倍差：只排 Windows/回收站 → 172.6 万文件 / 74.7 秒；再排 AppData、
ProgramData、Temp、assembly 这些 → 95.1 万文件 / 7.8 秒。差的那 77 万几乎全是 AppData 里
21 万个 `.py` 和 16 万个 `.pyc`——没人会去搜它们。

**内容索引只吃文档目录**（默认可加）：`文档`、`下载`、`桌面` + 数据家下的 `material`/`outputs`/
`exports` + 仓库 `docs`。全盘 1.9 万个"可抽文档"里有 1.5 万个是软件自带的 txt（Program Files 里），
抽了既慢又没用。

**U 盘 / 网络盘不进默认口径**：拔掉的盘会让每轮扫描卡在超时重试上，表现成"索引再也不更新了"，
而用户根本不知道是盘的事——要搜就在设置里手动加目录。

## 🔤 中文全文：为什么自己切二元组

内置 SQLite 的 FTS5 有，但两个现成分词器都不能用（实测）：

- `unicode61` 把「关节不舒服」整串当**一个词**，`MATCH '关节'` 命中 **0**；
- `trigram` 要求查询词 **≥3 字符**，中文两字词照样搜不到。

所以正文入库前在 Python 里切成**二元组**（`关节不舒服` → `关节 节不 不舒 舒服`），查询时同样切，
再用 **FTS5 短语表达式**（`"关节"`）匹配。用短语而不是逐词 AND 是为了保住"连续子串"语义：
文档里 `axbc` 切成 `ax/xb/bc`，查 `abc`（切 `ab/bc`）逐词 AND 会误命中，短语不命中。
**单字**切不出二元组，退回 `LIKE` 兜底。

写库与查询走同一个 `normalize()`（剥空白 + 转小写），口径差一点就永远搜不到。

## ♻️ 增量扫描的签名

**全盘照走**（7.8 秒本来就不贵），只对"签名变了"的目录做数据库差分。签名是
**目录自己的 mtime + 子项数（`dirs.mark`）两条一起**：

- 不能靠"父目录没改就不进子树"：子目录里新增文件不会刷新父目录的 mtime，剪子树必漏；
- 也不能只看目录自己的 mtime：Windows 上它粒度不够细，**同一秒里"加一个又删一个"时间戳能
  一模一样**——这条真踩过（增量轮报 `removed=0`，删除永远看不见）。子项数一跳，差分必然重跑。

两个补充口径：

- `dirs.seen` 记本轮有没有走访过，扫完统一清掉"整个目录已被删除"的残留行；
- **被 `stop` 打断的那一轮绝不做收尾清理**——没走到 ≠ 已被删除，清了就是"一退出搜索框整个索引
  就空了"。

`files.mtime` 只反映新增/删除：NTFS 上原地改文件内容不动父目录 mtime，所以"只改内容不增删"的
文件，文件名索引里那条 mtime 可能偏旧。**正文索引不受影响**——那边每篇都自己 `os.stat`。

老库升级：`CREATE TABLE IF NOT EXISTS` 对已存在的表**一个列都不加**，所以 `connect()` 里显式
`_migrate()` 用 `ALTER TABLE` 补 `mark` 列，同时 `INDEX_VERSION` 从 1 升到 2 让只按 mtime 建过的
库整库作废重扫。漏了 `_migrate` 的后果不是崩，是 `SELECT mtime,mark` 抛的 `OperationalError`
被 `scan_once` 的 `except sqlite3.Error` 吞掉 → **每个目录静默跳过差分，索引从此不再更新**。

## 📄 正文抽取支持矩阵

| 类型 | 走什么 | 上限 / 说明 |
|------|--------|-------------|
| `.txt` `.md` | 纯 stdlib，多编码轮试 `utf-8 → utf-8-sig → gbk → cp936` | Windows 下的 txt 常是 ANSI/GBK，项目踩过这个坑 |
| `.docx` | `zipfile` + 去 XML 标签（`word/document.xml` + 脚注/尾注） | 零新依赖 |
| `.pptx` | `zipfile`，**逐页** `ppt/slides/slideN.xml` | 最多前 80 页；只读 slide1 的话第二页往后永远搜不到 |
| `.xlsx` | `openpyxl(read_only=True, data_only=True)` | 已有依赖 |
| `.pdf` | `pypdf`（**函数内懒导入**） | 最多前 80 页；单页坏了不影响整本；没装 pypdf 就只跳过 pdf |
| `.doc` `.xls` `.ppt` | 不抽（老版二进制格式纯 stdlib 抽不出来） | 只进文件名索引 |

统一的三条形：

1. 跳过 `~$` 开头的 Word 锁文件（实测 162 字节的假 zip，喂进 `zipfile` 就 `BadZipFile`）；
2. 超过单文件上限（默认 20MB，设置里可改）不抽——一个 500MB 的 PPT 里多半是图；
3. **任何异常都返回 `""`**：一个坏文件绝不能把索引线程带崩。

正文最多存 2 万字（`DOC_BODY_KEEP`）。不封顶的话一个 100KB 的 txt 连切词能撑出 300KB 索引，
两万个文档就是几个 GB。每 50 个文档 `sleep 0.2` 限速——用户正在剪视频时后台吃满 CPU 就会被
当成"软件抢性能"。

## 🗄 索引库在哪、多大、怎么重置

独立库 `<数据家>\data\file_index.db`（安装版在 `%LOCALAPPDATA%\AIGC视频助手\data\`，
开发态在仓库 `data\`）。**绝不塞进 `aigc.db`**：索引随时可以整库删掉重扫，连累业务库
（历史任务/看板）是绝对不能接受的。

实测 95 万文件 + 1,496 篇文档＝**729 MB**，比最初 100–200 MB 的估计大 3–4 倍。大头在两处：
`files` 表把 `path / dir / name` 三列都存了（同一段目录字符串重复一遍），`docs_fts` 除了原文
还存一份长度翻倍的二元组。这层没做去重压缩是刻意的——差分与 LIKE 查询都要直接按列命中，
拆表会让每轮扫描的 SQL 复杂一个量级。

要收体积就两条路：设置页「🔁 立即重建索引」（清空后重扫，偏好一项不动），或者
`fileindex.vacuum()`（大批文件消失后回收磁盘；`VACUUM` 不能在事务里，所以单独一个函数）。
库真坏了（读不出来、锁死）直接把那个 `.db` 文件删掉重启即可——**索引没有保留价值**。

写库用模块级 `RLock` 串行、每线程一条连接（sqlite 连接跨线程用会直接抛），`WAL` 模式让
"扫描线程写 / UI 线程读"不打架。这些都是 `store/db.py` 的既有口径，不另立一套。

## 📦 打包注意

`pypdf>=5.0` 已进 `requirements.txt`，并且**必须显式列在 `--hidden-import` 里**：

- `build.bat`：标准版与创作版（入口都是 `desktop.py`）已加 `--hidden-import=pypdf`；
- `.github/workflows/build-windows.yml`：GUI 那一步同样加了，并且**新增一个永远跑的
  验收步骤**：`grep pypdf build/*/Analysis-00.toc`，没命中就直接 `exit 1`；
- 三个 `desktop.py` 入口的 `.spec`（`aigc_creator`/`aigc_slim`/`AIGC视频助手`）也写了
  `'pypdf'`，但要注意 **`.gitignore` 包掉了 `*.spec`**：它们是 PyInstaller 生成的产物，
  只改 spec 等于没改——真正能分到同事手上的口径在 `build.bat` 与 CI 里；
- 两个 CLI 入口（`main.py`）不带面板，所以没列 `pypdf`：白塞 400KB 到一个用不到的包里。

为什么要这么麻烦：`core/fileindex._pdf_text()` 是在函数体里 `from pypdf import PdfReader`，
PyInstaller 的静态分析扫不到函数体里的 import。漏了**不会报错**，就是
**开发机能搜 PDF、打包后静默搜不到**——而“静默”才是最难查的那类 bug。
